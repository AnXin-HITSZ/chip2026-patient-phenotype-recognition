## 1. HPO 人类表型本体

### 1.1 是什么、由谁维护

人类表型本体（Human Phenotype Ontology, HPO）于 2008 年创建，提供一套标准化、可计算的词表来描述人类疾病中的**表型异常（phenotypic abnormalities）**与临床特征，广泛用于罕见病诊断、基因-表型关联分析、临床数据库术语标准层。每个概念有稳定唯一的标识符（形如 `HP:0000118`）、首选名（`name`）、一组同义词与一段定义。HPO 由 **HPO Consortium** 与 **Monarch Initiative** 联合维护（核心人物含 Peter Robinson、Sebastian Köhler 等），这一点在本任务 `hp.obo`（版本 `hp/releases/2026-06-23`）文件头 `property_value: dc:creator` 中即有声明。

### 1.2 顶层结构与为何只评 HP:0000118

HPO 形式上是一个**有向无环图（DAG）**，根节点 `HP:0000001 All`。在 2026-06-23 版本中，根的直接子节点为以下子本体：

| HPO ID | 名称 | 是否计入评测 |
|---|---|---|
| **HP:0000118** | **Phenotypic abnormality（表型异常）** | ✅ 唯一评测分支 |
| HP:0000005 | Mode of inheritance（遗传方式） | ❌ |
| HP:0012823 | Clinical modifier（临床修饰语） | ❌ |
| HP:0040279 | Frequency（频率） | ❌ |
| HP:0032443 | Past medical history（既往史） | ❌ |
| HP:0032223 | Blood group（血型） | ❌ |
| HP:0020228 | Biospecimen phenotypic feature（生物样本表型） | ❌ |

只评 `HP:0000118` 的原因：其他分支描述的是**元信息/上下文**（如何遗传、发生频率、严重度修饰、既往史、血型、样本类型），而非「患者身上的异常表型本身」。`HP:0000118` 是最大的分支，其下约 23 个直接子节点大致对应器官系统（神经 HP:0000707、心血管 HP:0001626、眼 HP:0000478、代谢/稳态 HP:0001939、肿瘤 HP:0002664、肌肉骨骼 HP:0033127 等），越深越具体。

> 经本仓库 `scripts/inspect_data.py` 解析实测：`hp.obo` 共 **20,413 个 `[Term]`**；其中 **HP:0000118 分支后代（含自身）19,087 个**，`is_obsolete: true` 词条 577 个。

### 1.3 hp.obo 关键字段

文件为 OBO Flat File 1.2。每个 `[Term]` 块的核心字段（下例为真实词条）：

```
[Term]
id: HP:0000010
name: Recurrent urinary tract infections
alt_id: HP:0000094
def: "Repeated infections of the urinary tract." [https://orcid.org/...]
synonym: "Recurrent UTIs" EXACT abbreviation []
synonym: "Urinary tract infections" EXACT layperson []
xref: SNOMEDCT_US:197927001
xref: UMLS:C0262655
is_a: HP:0002719 ! Recurrent infections
```

- `synonym` 有四种作用域：`EXACT`（可等价替换）/ `NARROW`（更窄）/ `BROAD`（更宽）/ `RELATED`（相关）；并带类型子标签（`layperson` 通俗说法、`abbreviation` 缩写、`plural_form`、`uk_spelling` 等）。构建召回词典以 `EXACT` + `name` 为主，其余谨慎使用以免误命中。
- `xref`：到 `UMLS:`、`SNOMEDCT_US:` 等的交叉引用，可辅助消歧。
- `is_a`：父类关系，**同一词条可有多个 `is_a`（多父节点）**，构成 DAG。
- `alt_id`：被合并的旧 ID，应重定向到当前 ID。
- 过时词条：`is_obsolete: true` 标记，并给 `replaced_by:`（唯一，可自动替换）或 `consider:`（可多个，需人工判断）。

### 1.4 版本敏感性与词典/层次构建

必须严格用 **2026-06-23**：跨版本会有 ID 新增/合并/过时、定义与同义词变更，用错版本会导致金标 ID 对不上而**直接丢分**。可操作步骤：

1. **解析**：逐块读 `[Term]`（可用 `pronto` / `obonet` 或自写按空行分块的解析器）。
2. **建 `name+synonym → HPO ID` 词典**：收集 `name` 与全部 `synonym`，小写化、去多余空格、可选去连字符归一；`alt_id` 也指向当前 ID；同字符串命中多 ID 时保留候选集交由消歧。
3. **处理 obsolete**：不把过时 ID 作为输出目标；历史命中过时 ID 用 `replaced_by` / `consider` 重定向。
4. **过滤到 HP:0000118 后代**：由 `is_a` 建 child→parent 邻接表，从 `HP:0000118` BFS/DFS 取全部后代白名单，其余分支命中一律丢弃。
5. **祖先/后代用于去重与归并**：DAG 有多父节点，父子同时被预测时是否合并要严格对照评测口径（通常保留最具体节点，除非规则要求上卷），不要盲目把后代折叠到祖先。

### 1.5 中英文对照与 CHPO

`hp.obo` 的 `name` / `synonym` 均为英文，PatientPheX 为英文 PMC 全文，检索主战场是英文。**CHPO（中文人类表型标准用语联盟）** 提供 HPO 概念的中文名与中文同义词，可作为**同义词扩展 / 中文侧检索**来源；但其覆盖版本可能滞后于 2026-06-23、翻译粒度不完全一一对应，使用时仍应以官方 `hp.obo` 的 ID/结构为唯一权威。

## 2. PMC 全文与 BioC 格式

### 2.1 PMC 全文、pmc_id 与 pmid

PatientPheX 每篇取自 **PubMed Central（PMC）** 公开全文。`pmc_id` 是数据集主键（全库唯一）；`pmid` 用于连接 PubMed 题录/MeSH，官方 README 说明其**可能为 `null`**（训练集 80 篇实测均非空）。只有落在 **PMC Open Access（OA）子集** / Author Manuscript 集合的文章才允许全文文本挖掘并可编程获取。实测本数据的 `full_text` 与 NCBI **BioC-PMC API** 输出逐字一致（即数据集在 BioC-PMC JSON 基础上筛段 + 人工表型标注得到）。

### 2.2 BioC 与 full_text 字段

**BioC** 是一种极简文本挖掘交换格式：文档由若干 **passage（段）** 组成，每段含 `offset`（该段首字符在整篇文章中的全局位置）、`text`、以及若干 `infon`（键值元数据）。本数据把两个 infon 提升为字段：`section_type`（粗粒度章节类别）、`type`（BioC passage 细粒度类型：`front` 题名 / `abstract` 摘要 / `paragraph` 正文段 / `fig_caption`、`table_caption` 图表说明等）。

训练集 80 篇实测的 `section_type` 分布与信息富集度：

| section_type | 段数 | 表型实体 | 密度(/10k 字符) | 患者提及 |
|---|---|---|---|---|
| CASE | 322 | 982 | 59.5 | 165 |
| ABSTRACT | 352 | 621 | 55.6 | 57 |
| RESULTS | 324 | 859 | 49.0 | 144 |
| INTRO | 421 | 1517 | 56.5 | 97 |
| DISCUSS | 512 | 1382 | 37.3 | 117 |
| FIG | 265 | 371 | 36.7 | 59 |
| TITLE | 80 | 60 | 67.3 | 6 |
| METHODS | 380 | 130 | 9.1 | 16 |
| CONCL | 84 | 103 | 34.4 | 11 |
| TABLE | 72 | 2 | 3.4 | 5 |

对**子任务 2（患者-表型关联）**，**CASE / RESULTS / ABSTRACT** 是患者临床表现最集中、患者提及最密的区域，应重点建模；FIG 说明里也常含表型，不可丢弃。本语料中 **TABLE 多数仅保留标题（caption），表体基本未收录**，故表格表型贡献有限；INTRO/DISCUSS 虽实体绝对数高，却多是背景疾病或他人病例，关联到「指定患者」时需谨慎。

### 2.3 offset 是「原始完整文章的全局字符位置」（最关键约定）

`patient.mention`、`entities` 的 `offset` / `length` 都相对**原始完整文章**，而非某段内的相对位置。`full_text` 只是原文的**子集**（筛掉了参考文献、部分图表等），但**保留了每段的全局 offset**——相邻段之间常有空洞（间隔 > 1 表示中间有段被删除）。因此**绝不能靠拼接 full_text 各段来定位实体**，否则坐标全错。

稳妥做法：以最大 `offset+len(text)` 建等长缓冲区，用空格填充空洞，再把每段文本写回其 `offset` 处：

```python
def build_global(segs):
    end = max(s["offset"] + len(s["text"]) for s in segs)
    buf = [" "] * end
    for s in segs:
        o, t = s["offset"], s["text"]
        buf[o:o+len(t)] = list(t)      # 按全局坐标回填
    return "".join(buf)

G = build_global(doc["full_text"])
for e in doc["entities"]:              # 断言校验
    assert G[e["offset"]:e["offset"]+e["length"]] == e["text"]
```

> 该断言在全训练集 100% 通过（实体 6027/6027、患者提及全部对齐），证明约定成立。本仓库 `scripts/inspect_data.py --check-offset` 即实现了此校验。

**保持 offset 对齐的注意事项**：任何清洗/分词都**不得改变字符数**。BioC unicode 版含非 ASCII 字符（希腊字母、连字符、特殊空白），必须按 Unicode 码点计数、UTF-8 读入，**不要做 NFKC 归一化、空白折叠或 HTML 反转义**等改变长度的操作；确需归一化时应另建「归一化↔原始」偏移映射表，最终输出仍换算回原始 offset。

### 2.4 处理长全文的工程建议

- **按 section 切块**喂给 ≤10B 模型，每块携带 `base_offset`，块内局部下标一律 `+base_offset` 还原为全局坐标再输出。
- 切块、分词都要维护 token→全局字符区间映射，避免边界错位（影响 mention-level F1）。
- 别丢 FIG/TABLE 的 caption（含表型）；提交前逐条断言 `text == G[offset:offset+length]`。
